# Bug reports and maintainer workflow

**External participation in NetWiv is limited to bug reports. External pull
requests and code patches are not accepted, regardless of whether they are
written manually, with AI assistance, or generated by AI.** This includes fixes,
features, tests and documentation changes. Feature requests and other
contribution proposals are not accepted.

The maintainer develops NetWiv with AI coding agents and owns its development
direction and implementation. This policy keeps review and maintenance work
within the maintainer's available capacity. It applies equally to all external
code submissions; AI use is not a criterion for acceptance or rejection.
External PRs may be closed without review.

## Reporting bugs

Search existing [issues](https://github.com/kim0522ms/NetWiv/issues) before
opening a bug report. Include:

- The NetWiv version or commit and relevant OS, architecture and .NET
  SDK/runtime versions.
- Minimal steps or a small reproduction project that demonstrates the bug.
- The expected behavior and what actually happened.
- Relevant error messages or short log excerpts, with personal information
  and credentials removed.

Reproduction code is welcome as part of a bug report; proposed implementation
patches are not accepted. Report behavior you have observed and distinguish it
from suspected causes, including when using AI to help prepare the report.
Report NetWiv problems here; an upstream report needs a separate reproduction
against that upstream project.

Include only environment details needed to reproduce the issue. Omit hostnames,
account names, personal paths, network addresses, serial numbers, identifying
hardware details and personal or customer content from reports and attachments.

The maintainer decides which reports to investigate and when. Filing a report
does not guarantee a response, a fix or a delivery date.

## Maintainer workflow

The remaining sections govern maintainer changes, including work performed by
AI coding agents on the maintainer's behalf. They do not open an external
contribution path or require bug reporters to implement or validate a fix.

Read the [design principles](docs/design-principles.md),
[development guide](docs/development.md) and [working agreement](AGENTS.md).
The [architecture](docs/native-architecture.md), [native ABI](docs/native-abi.md)
and [API status](docs/api-status.md) explain the boundaries between the C# SDK,
generated bindings, IPC/security policy and native desktop implementation.

Before implementing a new public API, dependency, supported platform,
distribution format or substantial redesign, record the problem and proposed
approach in a maintainer issue. Small, reproducible fixes and documentation
corrections can go directly to a maintainer PR.

## AI-assisted development and responsibility

**The maintainer is responsible for every part of each change, including
code, tests, documentation and claims generated by an AI tool.**

The maintainer follows the project's architecture and ongoing changes across
the repository. An agent working on one issue may not have that context.
Even a small local fix can change another platform's
behavior, break a consumer's build, or alter permissions and object lifetimes.
Your PR needs to make those dependencies and assumptions visible.

Before requesting review:

- Read the complete diff and be able to explain the problem, the approach and
  the affected execution paths. Do not submit generated output you cannot explain.
- Trace callers and consumers across boundaries touched by the change. Explain
  which neighboring behavior you checked and which risks remain.
- Run the relevant checks and inspect their results yourself. An agent's claim
  of success, another model's approval or a green build is not runtime evidence.
- Check the provenance of copied or adapted material and preserve its notices.
- Briefly disclose material AI assistance in the PR: tools used, their role and
  what you personally reviewed and verified. Prompt histories are not required.

AI assistance does not reduce the validation standard. Reviewers are not expected
to reconstruct missing reasoning or finish an unverified patch. Be available to explain the change,
address feedback and help investigate regressions attributable to it. This is
an engineering responsibility, not a claim that anyone can guarantee zero bugs.

## Branches and commits

Create a topic branch from the latest `main` using:

```text
<type>/<short-description>
<type>/<issue-number>-<short-description>  # when there is a related issue
```

Use lowercase ASCII words separated by hyphens. Name the purpose of the work,
not the agent, workstation, date or worktree that produced it.

| Type | Use | Example |
| --- | --- | --- |
| `feat` | New or expanded behavior | `feat/instance-commands` |
| `fix` | Correct a defect | `fix/8-installer-paths` |
| `refactor` | Restructure without changing behavior | `refactor/command-dispatch` |
| `docs` | Documentation only | `docs/contributing-guide` |
| `test` | Tests or fixtures only | `test/invocation-lifetime` |
| `ci` | Build, validation or release automation | `ci/release-packaging` |
| `chore` | Dependency or repository maintenance | `chore/update-dependencies` |

Keep one purpose per branch and PR. Prefer PR titles and authored commit subjects
such as `feat: support instance commands` or `fix: preserve installer ownership`;
explain the reason in the body where needed. Do not mix cleanup, formatting or
unrelated dependency upgrades into a functional change.

Keep your branch current with `main` and rerun affected checks after resolving
conflicts. Merging `main` into an already shared branch is fine; avoid rewriting
history that others are using. Delete the topic branch after merge when no work
still depends on it. This convention applies to new branches; existing PRs do
not need renaming just to comply.

Releases currently come from version tags on `main`, so routine packaging work
uses `ci/*`, not `release/*`. Reserve `backport/*` for an agreed fix to an older
maintained release line, not for adding support for an older .NET runtime.

## Developing a change

Follow the [development guide](docs/development.md) for host prerequisites,
native builds and test commands. Use the pinned toolchains and dependencies;
consumer apps and framework development have different build requirements.

Keep the change small enough to review as one coherent unit, but complete its
behavior, documentation and tests together. Add a regression test for a bug and
exercise relevant failure paths, cancellation, cleanup and invalid input. For
new or substantially changed test targets, inspect coverage to find missed
branches; coverage percentages do not replace behavioral checks.

Preserve public contracts where practical. Document intentional differences and
migration steps when behavior changes. Keep generated upstream inventories
reproducible from their source rather than hand-editing them. Changes involving
NativeAOT must be published **and executed** with NativeAOT. Managed execution
alone does not establish AOT compatibility.

## Validation and real-device evidence

> [!IMPORTANT]
> A code or behavior-changing PR must include evidence of validation on a real
> device running an affected target platform. PRs without adequate real-device
> evidence may be rejected or closed without a full code review, even when CI
> passes. Maintainers decide whether the evidence covers the change's risks.

A real device means physical hardware running the target OS and relevant
runtime. Remote access to that hardware is acceptable. Label VMs, containers,
headless sessions and hosted CI honestly: their results are useful, but do not
present them as physical-device or interactive desktop verification. A build,
mock runtime, screenshot of an editor, or AI-generated summary alone does not
show that the changed application behavior works.

Match the evidence to the change. You do not have to own every supported device,
but you must identify affected platforms and leave untested combinations marked
as unverified. Coordinate with another tester if necessary and credit their
report. Missing platform access is a reason to request help or keep a PR in
draft, not to mark a test as passed.

| Change | Expected evidence |
| --- | --- |
| Windows, WebView, menu, tray or window behavior | Run the affected scenario in a real desktop session; describe the interaction and result. |
| Installers or packaging | Install, launch, upgrade and uninstall the produced artifact as applicable; describe scope, preservation/cleanup behavior and failures tested. |
| SDK, IPC, DI, generators or shared native code | Execute a representative consumer on a real device through the affected path; include automated regressions and managed/AOT runs where relevant. Check affected platform boundaries. |
| Build or CI automation | Exercise the changed job or script and, when artifact output or behavior changes, run the resulting artifact on the target device. |
| Documentation or comments only | Explain why runtime evidence is not applicable; check links, examples and accuracy. Instructions claiming a working procedure still need evidence for that claim. |

For each device run, provide:

1. **Revision and environment:** tested commit SHA, execution type (physical,
   VM or headless), architecture, OS version, and relevant SDK/runtime and
   WebView/native dependency versions. Specific PC specifications and device,
   CPU, GPU or monitor model names are not required and must be omitted by default.
2. **Procedure:** exact commands or reproduction steps, configuration, artifact
   tested, and any relevant managed/AOT, privilege or installation mode.
3. **Results:** expected versus observed behavior and the outcome of the
   regression checks.
4. **Coverage and limits:** failure and cleanup scenarios checked, affected
   consumers/platforms, and anything not tested or not passing.

Summarize verification in the PR. After a meaningful revision, rerun affected
checks and update that summary. Use reproducible commands with generic paths.
Validation requirements do not call for a report collection system: do not add
environment inventories, diagnostic archives or evidence retention/upload to
product code, test helpers or CI/CD, and do not commit per-run reports or logs.
Keep functional assertions, normal CI console output and release deliverables.

Personal information includes details that can identify a person or their
environment indirectly or in combination, not only names and credentials.
Do not publish credentials, identifying hardware details, hostnames, account names, personal
paths, network addresses, serial numbers or personal/customer content. Minimize
environment details to what is necessary to explain the validation. Review the
PR body, complete diff, logs, screenshots and uploaded artifacts before submission;
real-device evidence does not require disclosure of a tester's hardware inventory.
If a detail is necessary but potentially identifying, or its sensitivity is
unclear, withhold it and agree on the exact disclosure and purpose with the user
before publishing. Keep that agreement in the user's approved private local
storage outside the repository and published artifacts, not in the public report.

The [CI workflow](.github/workflows/ci.yml) supplies additional platform checks.
Read failing logs before changing code or requesting a retry. Do not use repeated
full CI runs as a substitute for local reproduction, and do not weaken tests to
make a build green. A passing pipeline complements the evidence above.

## Submitting a pull request

This workflow is for maintainer PRs only. External PRs are not accepted.

Target `main` and complete the [PR template](.github/pull_request_template.md).
Start with the concrete problem and resulting behavior, then explain the design
choice, affected consumers, test results and remaining limits. Link related
issues and include documentation or migration guidance alongside API changes.

Use a draft when investigation or required verification is incomplete. For a
runtime-evidence exception, explain why the change has no applicable runtime
path; the maintainer decides whether that justification is sufficient.

Respond to review with explanations and focused revisions. After fixing review
findings, update the evidence and request another review. Consolidate updates
rather than posting a comment for every intermediate attempt. Treat reviewers
and contributors respectfully; disagreements should focus on behavior and
technical tradeoffs.

Merge requires maintainer acceptance and the applicable repository checks.
Automated review approval alone is not acceptance. A maintainer may request a
smaller scope, additional evidence or a different design, or decline a change
that does not fit the project's direction or maintenance capacity.

## Licenses and attribution

Include only material you have the right to distribute under the repository's
[license](LICENSE-APACHE). Preserve existing copyright and license notices.
Identify borrowed or ported material, link its source and update [NOTICE](NOTICE)
and [third-party notices](THIRD-PARTY-NOTICES.md) where applicable. AI-generated
output needs the same provenance review as manually written changes. Do not
introduce upstream branding that makes NetWiv look like an endorsed product.
